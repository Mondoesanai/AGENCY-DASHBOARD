## Status key

| Mark | Meaning | Rule |
|---|---|---|
| `[ ]` | not started | — |
| `[~]` | in progress | — |
| `[b]` | **built, not verified** | Code exists and is wired. No test or live observation yet. **Not completion.** |
| `[x]` | **built and verified** | Must have a row in `VERIFICATION_REPORT.md` at L1 or higher. A tick without that row is invalid. |
| `[!]` | **externally blocked** | Waiting on a decision, credential, purchase or calendar time *outside this codebase*. Must name what would unblock it. |

Two rules that bind both the builder and the supervisor:

1. **No requirement may be deleted, reworded weaker, or silently dropped to declare progress.**
   If a requirement turns out to be wrong, it gets struck through with the reason recorded —
   never erased.
2. **`[b]` is never upgraded to `[x]` by assertion.** It takes an executed check with an
   observed result.

## Hard constraints discovered in inventory (do not design around these being false)

| Constraint | Detail | Consequence for this build |
|---|---|---|
| **Vercel Hobby = 12 serverless functions, all 12 used** | `api/` has exactly 12 `.js` files | **No new API files.** Every new endpoint routes through `api/admin.js` (`?do=` switch, existing pattern) or an existing public file (`api/collect.js` for unauthenticated webhooks). |
| **No SQL database** | Storage is Upstash Redis KV via `lib/store.js` | Contacts/campaigns/ledger use KV with explicit secondary-index sets (`sadd`/`smembers`), the pattern already used by `registry:slugs`. Scales fine to the "thousands of contacts" target; no joins. |
| **store.js has no `del`, no sorted-set range, no transactions** | Only get/set/sadd/smembers/mget/incr/zincr/ztop/pfadd/pfcount; `set` supports `{nx, ex}` | Added `del` + `srem` + atomic `reserve`. `incr` is atomic (safe for budget counters); `set {nx}` is the lock primitive (already used by `revisions:lock`). |
| **No build step, no framework** | Vanilla single-file SPA `public/index.html` (2334 lines), plain ESM in `lib/` | No React/Tailwind. New UI extends the existing SPA + its CSS tokens. No bundler to add. |
| **Function timeout 60s (300s on `api/admin.js`)** | `vercel.json` | Long work must be chunked into bounded ticks, like the existing `lib/tick.js`. |
| **Cron: one daily Vercel cron + GitHub Actions + public rate-limited poke** | `vercel.json` crons, `.github/workflows` | Reuse `lib/tick.js` driver; do not invent a new scheduler. |
| **Email today = Resend (transactional)** | `lib/winsrecap.js`, `lib/revisions.js` | Resend's terms are for transactional/opt-in mail. **Cold prospecting needs separate infrastructure** — see Open Decisions. |
| **Deliverability ramp is calendar-time bound** | New sending domain has no reputation | Cold send volume must ramp over ~2–4 real weeks. Code cannot compress this. |

These answer a different question from R9.2's ladder: that one asks *did the message work?*, this asks *did it arrive, and did it do harm?* — and the design is about never combining the two. **A harm signal never improves a variant's standing.** Complaints and opt-outs are not negative conversions to be netted off against replies; a system that subtracts one from the other will eventually recommend the message that generates the most complaints, as long as it also gets more replies. They are reported alongside with their own direction, and the breakdown has no net, no score and no winner. **Delivery is a denominator, not an achievement** — "3 replies from 50 sent" is wrong if only 20 arrived — and where delivery is unknown the report says the rate is over what was *assigned*, adding that those are not the same number, rather than quietly pretending. A **hard bounce is deliberately not harm**: it measures list quality, not message quality, and an arm with more bounces was probably handed worse addresses. **A machine click is not a click.** Corporate scanners open every link in a message within seconds of delivery, and counting those as engagement makes the most aggressively filtered recipients look like the most interested ones. The strongest signal is shape rather than user agent — a click two seconds after delivery, or every link opened in one burst — and a missing user agent on its own is explicitly too weak to condemn a click, needing a second signal before it decides. Wired where the facts actually arrive: `applyDeliveryEvent` fans each provider event out to the running arms, and `recordBookingLinkClick` classifies at the point the click lands. An **open records nothing at all**, which is R9.4 arriving a cycle early. Twelve negative controls, all twelve biting, including one that nets harm off against replies and one that turns an open into a secondary outcome. One control needed its needle corrected before it read anything — a reminder that a control which does not apply proves nothing, same as the one two cycles ago that was injected after the branch it meant to break.
- **2026-10-01** — R9.4, which is not a preference about metrics. **An open rate stopped measuring attention in 2021**, when Apple Mail Privacy Protection began pre-fetching the tracking pixel for every message sent to its users whether or not anyone reads it; Gmail has proxied and cached images since 2013, so one fetch covers every later re-read; and security appliances fetch everything before delivery. What is left is substantially a measurement of **which mail clients the recipients use** — optimising a message against it optimises for writing to people with Apple devices. Raw clicks have the same shape, less severely: they include every scanner that walks the message, so the most heavily filtered recipients look like the most interested ones. So `lib/ranking.js` is a **gate, not a report**. Only the four primary outcomes may order variants, because each required a person to do something, and every refusal carries its specific reason rather than a bare "not allowed" — a rule without a reason is a rule people route around the moment it is inconvenient. Two design points worth keeping. The gate **refuses outright rather than substituting**: a caller asking to rank by opens gets an error, not a quiet swap to replies that would then be reported as opens. And ordering is explicitly **not a verdict** — sorting by a count is arithmetic, and whether the difference means anything is R9.5's job. Opens are still counted and still shown, because hiding a number invites someone to go and find it elsewhere, but they are shown with what they actually measure and with **no contamination percentage**: the share caused by Apple's pre-fetch is not knowable from our side, and a number there would be a guess wearing a percentage sign. The machine share of *clicks* is reported, because we classified those ourselves, and with no clicks at all it says nothing is known rather than reporting 0%. Wired into the real route: every experiment report carries the statement, and `?do=experiment-rank&metric=opened` is refused over HTTP with the Apple reason attached. Ten negative controls, all ten biting.
- **2026-10-01** — R9.5, the part of an experimentation system that is easiest to fake and most expensive to fake. Three decisions worth recording. **Wilson, not the textbook interval.** `p̂ ± z·√(p̂(1-p̂)/n)` is wrong exactly where this system lives: with 1 reply from 20 it returns a *negative* lower bound for a quantity that cannot be negative, and with 0 replies it returns [0, 0] — certainty from no information. The Wilson score interval behaves at small n and at zero successes, and the tests pin it against values that can be checked by hand (50/100 → 40.4–59.6%, 1/20 → 0.9–23.6%, 0/20 → 0–16.1%). That is not academic: the naive interval is precisely what lets a tool announce a winner from a handful of events. **The sample size is computed and stated even though the answer is discouraging.** Telling a 3% message from a 4% one at 95% confidence and 80% power needs **5,299 per arm**, 10,598 in total — about **424 weeks, or 8.2 years**, at the target of 25 prospects a week. The report says so, and says plainly that *this comparison cannot be settled by sending more; change what is being tested, not the arithmetic.* That is the single most useful true thing this system can tell its owner, because the alternative is months of reading noise as signal. **Below 30 outcomes nothing is said at all**, which is the requirement's own wording tested literally: two replies split 2–0 produce no winner, and a 5–0 split across 40 people still produces no winner. Past the floor, overlapping intervals are reported as *no difference detectable* — explicitly not as "the arms are the same", because this much data failing to separate them is not evidence they are alike. Repeated looking is counted: every read of the report increments a counter, and past five looks a separation is refused with the reason that checking repeatedly and stopping at the first apparent difference inflates the false-positive rate past the stated confidence, and that no correction for it is implemented. Eleven negative controls, all eleven biting — including removing the floor, swapping Wilson for the naive interval, and reading an overlap as a difference. One crashed rather than failing (the unguarded dereference pattern, now the fourth time) and is guarded.
- **2026-10-01** — R9.6. Comparing variants to each other answers *which of these is better?* It cannot answer *is any of these better than what we were already sending?* — and those come apart in the case that matters: if every new wording is worse than the current message, an A/B test still names a winner, the least-bad of a bad set, promoted with a straight face. The holdout is the only thing in the design that can detect a whole experiment being a regression, which is also the finding nobody running it wants, which is exactly why it is structural rather than optional. So the rules are enforced at four points: a holdout is **added at creation** if not supplied, **refused at removal**, **never reassigned out of**, and **reported first**. The rule that actually bites is not the one at design time — it is three weeks later, when someone wants more traffic on the variant that looks promising and the baseline is in the way, which is precisely when it is worth most. That refusal names the reason. Two things fell out of building it. The arity check used to demand two arms *before* the holdout was added, so **one variant against the baseline was refused** — and "is this new wording better than what we send now?" is the question most worth asking, so the old rule would have pushed anyone wanting it into inventing a second variant they did not want. The ordering is now holdout-first, and one variant is a valid experiment. The second was worse: `updateVariants` ran `withHoldout` *before* the guard, so an edit that dropped the baseline was **silently repaired and reported as applied** — the caller would believe their change took effect while the opposite happened. The guard now runs against the proposal, and a dropped baseline is refused out loud. Twelve negative controls, eleven biting immediately. The twelfth — removing the baseline-first sort — did not, because my test watched a tally whose holdout was already first by construction: the test was observing the input rather than the behaviour. Re-tested with the baseline listed last, it bites.
- **2026-10-01** — R9.7. The failure this prevents is undramatic: opening the dashboard in six weeks, finding the message has drifted into something nobody would have approved, and having no way to answer *when did this change, who changed it, what was it before?* — let alone put it back. Three properties, in the order they get skipped. **Reversible**: every entry stores the previous value, not only the new one. A log that records "weights changed" is a diary; a log that records what they were is an undo, and the difference is one field and the entire value of the exercise. **Bounded**: the owner sets what may change unasked and by how much, as settings rather than constants — `allowAutomaticChanges` defaults to **false**, so nothing in this system alters a live experiment by itself today, and the caps (20% of traffic per change, three changes a week, owner-only for starting/stopping and for moving someone between arms) already apply to whatever is built later. Unreadable bounds resolve to the strictest reading, not the permissive one. **Attributed**: "owner" and "automatic" are different facts, and that is the first question after any surprise; an unrecognised actor is refused outright. The undo is itself logged, so the ledger shows the revert as well as the change.

  The reviewer's flag last cycle was correct and worth stating plainly: `mayReassign` had been written, unit-tested, and **had no caller**. The holdout rule was being kept by the *absence* of any reassignment path rather than by enforcement — the same orphan-module failure I have flagged in other people's work six times in this build, written by me. Closing it meant building the path: `reassign()` now exists in `lib/experiments.js`, consults `mayReassign` first and `mayChange` second, and `revertExperimentChange` re-checks the holdout rule on the way back, because an undo is otherwise a way around it. `setExperimentState` and `updateVariants` now record before/after too, and four owner-gated admin routes expose the ledger, the bounds and the revert. - **2026-10-01** — R9.8. R9.1 already refused to NAME any of the six as the variable under test, and on its own that is close to useless: a variant's content is free text, so an experiment declared `variable: 'subject'` whose arms read "A quick question about your website" and "Half price this week only" **is a price experiment wearing a subject-line label**, and nothing about the declared variable stops it. So the prohibition is enforced where the variation actually lives, in three layers. **Layer 1** is the declared variable (R9.1). **Layer 2** reads what the arms say — currency amounts, discounts, anything offered free, guarantees, ranking and multiplier claims, a different sender or platform identity, any restatement of the opt-out, and any claim of a consent that was not given — at creation *and* at the edit, which is the likelier place a clean experiment acquires a guarantee. The detectors are deliberately blunt and will occasionally refuse a harmless sentence: the cost of a false refusal is rewording one arm, the cost of a miss is a price experiment running for a month against real prospects, and every refusal names the arm, the field and the phrase so rewording takes seconds. **Layer 3** is the write boundary, and it exists because of R9.7's undo. A revert takes a logged `before` and hands it to an applier, so a change logged against a suppression record, the pricing settings or a budget could be "undone" straight into it — the ledger would be a second way to write to each of those with none of their own guards in the way. `revertChange` now refuses a protected target, and an unreadable target is refused too, because a write nobody can classify is not a safe write.

The admin route also reported a refusal as the new bounds; it now returns the refusal.

- **2026-10-01** — R9.9. Two decisions carry this one. **The first is that it may stop and may never start.** A wrong stop costs a few days of outreach the owner undoes in one click; a wrong resume costs the sending domain, and with it every message this business sends. So `enforce` only ever writes a stop, `clearStop` refuses any actor that is not the owner — refused at the write rather than by a convention someone has to remember, because "let's make this self-healing" is exactly the change that arrives later — and the refusal gives the reason that makes it non-negotiable: *"the numbers recovered" and "nothing is being sent, so nothing is bouncing" are the same numbers, and only one of them means it is safe to start.*

  **The second is the denominator, and it is the whole engineering problem.** At ~25 messages a week, one hard bounce is 4% and two is 8% — over any sane threshold, and also telling you almost nothing. A trip that fires on that fires most weeks, gets switched off within a month, and then protects nothing; the failure mode of a safety trip is not being too slow, it is being so noisy that it is disabled. So the rate triggers use the **lower bound of the Wilson interval** — R9.5's arithmetic, deliberately reused rather than reimplemented — and stopping means *we are confident the true rate is above the line*, not *this small sample looked bad*. Two bounces in 25 warns and explains that the sample is why nothing stopped; 48 in 400 stops. The exception is complaints, and it is arithmetic rather than a special case: Gmail and Yahoo publish 0.10% as the level to stay under and 0.30% as the line where filtering starts, so one complaint in 30 has a lower bound of 0.59% and *is* decisive — when the threshold is that small, a single event is the evidence. Two complaints also stop sending regardless of denominator, because the provider does not wait for our sample to become significant.

  Three things fell out of building it. **The scope was wrong first**: I had the trip writing the global automation pause, which also stops client site improvements — a prospect's address bouncing is not a reason to stop work paying clients are waiting for. It now writes its own flag that `sendReadiness` reads as a blocker, so `maySend` refuses while everything else carries on, and the test asserts the global pause is untouched. **A perfect record warned**: with a 0.30% threshold the upper bound of 0-in-500 is still 0.76%, so the "it could already be worse than it looks" rule fired on zero complaints — at this volume it would have warned for ever, which is the exact noise problem in the thing built to avoid it. That warning now needs at least one real event behind it. And the counters were **lifetime totals**, which cannot drive a safety trip: a bad week last year would keep it stopped for ever and would dilute a bad week now, so delivery events are also bucketed per day and the window rolls over 14.

  The stop also had to be *findable*. Outreach stopping itself is the one thing here the owner cannot learn any other way — nothing errors, nothing looks broken, messages simply stop — so it is an item in "what needs you", ranked below a paying client's stuck request and above a waiting reply, carrying the numbers and what to do. Verified in Chrome at both viewports.
